# E4 QoS 严格优先级

| | |
|---|---|
| 实验编号 | E4 |
| 建议课时 | 45 min |
| 难度 | 进阶 |
| 前置知识 | 拥塞、区分服务（DiffServ）、优先级调度 |
| 对应代码 | `satviz/experiments.py::_run_e4`，判据源自 `tests/test_phase3.py` Test 4 |

## 1. 实验目的

- 理解**严格优先级调度**（Strict Priority）的工作机制与代价；
- 定量观察拥塞下"高优先流受保护、尽力流承担丢包"的区分服务效果；
- 讨论 QoS 保障的边界：优先级解决不了什么问题。

## 2. 预备知识

当多类业务共享一条瓶颈链路时，严格优先级调度**总是先发高优先队列**，
低优先（尽力）业务只能使用剩余容量。设瓶颈容量 C，高优先到达率 λ_H：

- λ_H·s < 1（高优先未占满容量）：高优先几乎无排队；瓶颈的拥塞
  （排队 + 丢包）全部转嫁给尽力流；
- λ_H·s ≥ 1（高优先过载）：高优先自身也拥塞——优先级不创造容量。

本实验配置：

| 参数 | 值 |
|------|-----|
| 拓扑 | srcH / srcL → R1 → GS（共享瓶颈） |
| 瓶颈容量 | 1 Mbps（≈ 83 pps @1500 B） |
| 高优先流 | srcH → GS，60 pps（PRIO_HIGH） |
| 尽力流 | srcL → GS，60 pps（BEST_EFFORT） |
| 队列容量 | 30 包/端口 |
| 预热 / 测量 | 55 s / 5 s |

两流合计 120 pps > 83 pps，瓶颈处于超载 ~44% 的拥塞状态；
但高优先 60 pps < 83 pps，理论上应被完全保护。

## 3. 实验步骤

1. 启动平台，打开 **「教学实验」** 面板；
2. 展开 E4 卡片"实验参数"核对上表；
3. 点击 **「运行实验」**：55 s 拥塞预热 + 5 s 测量窗（约 30 s 实际时间）；
4. 核对三行判据，重点比较两类流的 e2e 时延与丢包率的数量级差异。

## 4. 判据与记录

| 判据 | 关系 |
|------|------|
| 高优先时延 | HIGH < BE |
| 高优先丢包率 | HIGH < BE |
| 尽力流承担拥塞 | BE loss > 0 |

示例实测（固定种子 11）：

```
HIGH: e2e = 35.6 ms,  loss = 0.000
BE:   e2e = 1064.9 ms, loss = 0.605
```

尽力流时延放大约 30 倍、丢包 60.5%——拥塞代价几乎完全由尽力流承担。

## 5. 思考题

1. 若把高优先流从 60 pps 提到 90 pps（超过瓶颈 83 pps），
   高优先流还能被保护吗？这说明 QoS 的本质是什么？
2. 严格优先级可能造成尽力流"饿死"。加权公平排队（WFQ）如何
   缓解？工程上为什么常把两者混合使用？
3. 结合主平台的文件传输功能：把一次传输设为高优先（prio=0）重跑，
   观察其在拥塞链路上的表现是否符合本实验的预测。
